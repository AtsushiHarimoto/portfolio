# 09.16 多 AI 模型切換策略 — 省 Token 的分工實戰指南

> **類型**: 最佳實踐 + 成本控制
> **日期**: 2026-03-26
> **來源**: 多 AI 協同實戰經驗

---

## 摘要

在 Moyin 的進階開發與工作協同環境中，我們配備了具備不同屬性的 5 類 AI 工具。隨著專案複雜度不斷上升，每一次的 API 請求都代表著運算資源與成本的消耗。因此，建立一套精準的「多 AI 模型切換策略」，成為了確保系統高效、低成本運作的核心關鍵。

這套策略的基礎在於：根據具體任務的推理難度、邏輯複雜度以及處理量，動態分配最適合的 AI 模型。透過特製的 Skills 基礎設施，我們能將高價值的 Token 預算聚焦在刀口上，同時把例行性的代碼編寫、文檔整理與大批量工作，委派給相對低成本甚至零成本的模型來負責。

妥善運用這樣的分工模式，不但能大幅避免「大材小用」造成的燒錢問題，也能防範「小材大用」導致的低級邏輯錯誤，完美平衡系統的時間效率與產出品質。

> [!NOTE]
> 💡 **白話文解釋**：想像你在經營一家頂級餐廳，你會花重金請一位米其林主廚（ Claude Opus ）親自去後廚洗菜切洋蔥嗎？肯定不會（太燒錢了）。反之，你也不會讓剛入行的學徒（低端模型）去主導下季的菜單設計（砸招牌）。正確的做法是：主廚負責定菜單與抓出味道不對的問題（Debug），二廚（Sonnet）按標準流程烹調，學徒（Gemini/Qwen）專心處理備料和洗碗。這就是我們多 AI 切換的核心哲學。

## 背景

在日常開發迭代中，開發者常有路徑依賴，習慣將所有問題一律拋給當前最強的模型（例如 Claude Opus）。然而這會產生兩個嚴重後果：第一，API 成本將以驚人的速度暴增；第二，重型模型在執行簡單任務時的等待延遲過高。反過來，若是為了省錢全用基礎或免費模型處理架構問題，則頻繁出現幻覺、偷寫假代碼，反而消耗更多時間去除錯。**為什麼要切換模型？** 正是為了在「成本」、「速度」與「智力」這個不可能的三角之中，找到每一件任務的最佳落腳點。

## 詳細內容

### 1. 模型陣容與核心分配矩陣

根據 CLAUDE.md 中所規範的 AI 分配規則，目前環境中共有以下 5 種主力模型可用：

| 模型/工具 | 實際使用者 | 適用任務 | 成本 |
|----------|---------|---------|------|
| **Claude Opus** | Claude Code（切換模式） | 小說/ASMR創作、複雜架構決策、原因不明的 bug | 最貴 |
| **Claude Sonnet**（預設） | Claude Code | Skill 開發、中度 coding、搜尋、除錯、按計劃執行 | 中等 |
| **Antigravity** (Gemini) | 透過 ZeroGravity proxy `localhost:8741` | 前端設計、git 操作、routine coding、文檔寫作、腳本生成 | 低 |
| **Codex** (GPT-5.4) | codex CLI | Code review、長文件審查、品質把關 | 中等 |
| **本地 Qwen3.5-27B** | `localhost:38001` | 批量抽取/分類/標註、Game LLM、大量重複性任務 | 零成本 |


### 2. 核心判斷法則

當準備委派任務時，請遵循以下這套標準判斷法：
*   💡 **列表與比較任務** → 預設交給 **Sonnet**
*   💡 **跨領域深度推理** → 升級請出 **Opus**
*   💡 **按既定計劃執行** → 推薦使用 **Sonnet**
*   💡 **原因不明、極難抓取的 bug** → 直接召喚 **Opus**


### 3. Skills 基礎設施

為支援上述框架，我們實作了多套代理與橋接工具，請依照以下規範使用：

#### Antigravity Skill
*   **用途**：委派輕量或重複性較高之任務給 Gemini。
*   **入口**：`localhost:8741/v1/messages`（由 ZeroGravity proxy 代理）。
*   **模型**：根據需求切換 `gemini-3.1-pro`（較複雜）或 `gemini-3-flash`（極快速）。
*   **⚠️ Prompt 長度規則**（**非常重要**）：
    *   **≤ 500 chars**：允許直接透過參數傳遞。
    *   **> 500 chars**：必須使用 Write tool 將內容寫入至 `docs/reviews/<name>.md`，然後再運用 `agy_file` 讀取該檔案。
    *   **絕對禁止**：禁止使用 stdin pipe (`|`) 或 shell 變數硬塞長文，這會導致伺服端嚴重截斷！
*   **用 Bash 執行的標準寫法**：
    ```bash
    curl -s http://localhost:8741/v1/messages \
      -H "x-api-key: dummy" \
      -H "anthropic-version: 2023-06-01" \
      -H "Content-Type: application/json" \
      -d "$(jq -n --arg m "gemini-3.1-pro" --arg p "你的 prompt" \
        '{model:$m,max_tokens:8192,messages:[{role:"user",content:$p}]}')" \
      | jq -r '.content[] | select(.type=="text") | .text'
    ```

#### ai-roundtable Skill
*   **用途**：三模型對抗式審查（Claude + Codex + Gemini），透過多方互鬥找出盲點。
*   **適用場景**：重要的架構級別決策、大型 PR 審查、技術方案評選。
*   **Personas (角色預設)**：
    *   🔴 **Elon (Claude)**：第一原理思想家，負責顛覆不合理的舊架構。
    *   🔵 **Guardian (Codex GPT-5.4)**：嚴格的品質把關者，死守邊界條件與資安規範。
    *   🟢 **Innovator (Gemini)**：創意與盲點獵人，尋找其他更聰明的實作捷徑。
*   **CLI 規範**：
    *   Codex：`codex --yolo --skip-git-repo-check -m gpt-5.4 --config model_reasoning_effort="high"`
    *   Gemini：`unset GOOGLE_CLOUD_PROJECT && gemini --approval-mode yolo`

#### web2api-roundtable Skill
*   **用途**：讓 Gemini + Grok 透過本地 Gateway 進行動態角色對話。Claude 僅作為旁觀者與執行者，不參與耗費 Token 的對話。
*   **入口**：`localhost:9009`
*   **適用場景**：需要多元視角激烈討論的「非代碼任務」，例如市場定位分析、產品創意腦暴。

#### 本地 Qwen
*   **入口**：`localhost:38001`（完全兼容 OpenAI API 格式）。
*   **適用場景**：大批量、重複性的純文本任務（零 API 成本，可隨意無限制調用）。
*   **限制**：無法勝任跨模組程式碼架構重構或高階邏輯推理。


### 4. Rate Limit (限流) 容錯策略

在運行多 AI 並行腳本（例如 ai-roundtable）時，經常會碰到 API 的 Rate Limit，請必須遵守：
1. **絕不重試**：遇到 rate limit 放棄該模型的此次回應，繼續執行剩餘步驟，防止阻塞主流程。
2. **透明告知**：在最終報告中明確註明「本次分析跳過了哪個模型（因限流）」。
3. **部分呈現**：即使少了某一位成員的看法，其餘模型的結果依然極具價值，**請照常彙整並呈現**。

## 實戰案例

### 案例 A：百萬字 Log 的關鍵錯誤提取
你的專案在凌晨崩潰，留下了好幾個總計上百 MB 的系統日誌。如果你把它塞給 Claude Opus，不僅會因為 Context Window 過大直接報錯，就算能跑也會消耗極端可怕的成本。
**實戰分工**：撰寫一個簡易腳本，將日誌分塊傳送給 **本地 Qwen3.5-27B (`localhost:38001`)**，要求其僅提取含有 "FATAL" 與對應 timestamp 的上下文。抓出具體的異常行為片段後，再將這短短數百字的關鍵片段提交給 **Claude Opus** 要求剖析「原因不明的 bug」。

### 案例 B：核心電商金流架構重構
開發團隊決定將過舊的單體架構拆分為分散式微服務，這影響了全站的交易準確性。
**實戰分工**：首先由 **Claude Sonnet** 負責整理當前架構。接著喚醒 **ai-roundtable Skill**，讓 Codex (🔵 Guardian) 尋找並攻擊資料庫 Transaction 鎖定可能帶來的 Race Condition；同時讓 Gemini (🟢 Innovator) 建議是否能導入其他 Event-driven 的輕量套件。收集三方激辯結果後，再由最高階的 **Claude Opus** 定期拍板做出最終的「複雜架構決策」。

## 常見陷阱

在使用這些 CLI 或指令工具切換模型時，極容易遭遇以下 5 個實戰地雷：

1. ⚠️ **Windows 背景 bash 缺 PATH 變數**：Codex 或 Gemini 在背景調用時，可能因為找不到 Node.js 而失敗。請務必在腳本指令前加上 `export PATH="/c/Program Files/nodejs:$PATH" &&`。
2. ⚠️ **Gemini CLI 403 錯誤**：如果 Gemini 發生 Authentication 403，通常是環境變數污染，請前置 `unset GOOGLE_CLOUD_PROJECT`。
3. ⚠️ **長 prompt 截斷問題**：使用類似 `echo "..." | codex` 或 piped 給 gemini 的方式會發生嚴重截斷！**必須**乖乖寫入實體檔案，讓 CLI 自己去讀檔。
4. ⚠️ **誤用 `--last` 恢復 session**：在多工環境下，`--last` 常常會指錯跑到某個背景掛起的毫不相干的任務中。**必須**依賴回傳的明確 Session ID 來接續對話。
5. ⚠️ **Thinking block 導致空輸出**：API 升級後，模型會回傳 "thinking" 類型的區塊。用 jq 如果沒寫好，就會抓到空白。**必須**過濾出 text 型態：`select(.type=="text")`。
