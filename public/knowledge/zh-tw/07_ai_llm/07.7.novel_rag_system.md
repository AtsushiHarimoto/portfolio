# 07.7 小說素材 RAG 系統搭建：三層混合檢索架構
> **類型**: 系統架構設計 > **日期**: 2026-03-26 > **來源**: 內部核心技術庫

---

## 摘要

本文章旨在規範處理大量網路小說語料庫（涵蓋晉江文學城、番茄小說等來源）的知識庫檢索系統搭建標準。我們針對言情、原耽、百合等 13 種細分領域，打造了一套全新的「三層混合 RAG 系統（Retrieval-Augmented Generation）」。

此系統的核心目標，是為 AI 小說創作輔助工具提供高精準度的素材檢索支援。透過「特定風格與段落比對」，系統能在海量文本中，迅速找出與作者當前寫作風格最相近的參考段落，為創作環節提供真實、優質的語境範本。

整體架構從輕量級的元數據過濾、純 CPU 高速運算的寫作指紋比對，一直到基於 GPU 加速的深度語義向量檢索，確保了系統在極端資料量下依然能維持毫秒級的響應速度與極高的語義相關性。

> [!NOTE] 
> 💡 **白話文解釋**
> 想像你在一個有幾百萬本藏書的圖書館找參考資料。
> 第一步（Layer 1），你告訴館員：「我要看現代言情，評分 4.5 以上的」，館員立刻幫你篩出一批書。
> 第二步（Layer 2），你跟他說：「我喜歡看那種短句多、對話多、情感起伏大的」，這就是「寫作指紋」，又篩掉了一大半。
> 第三步（Layer 3），你拿出一小段文字說：「就是要這個 Feel（語義）」，館員用他超強的記憶力（向量庫）直接幫你翻到最切合的那三頁。

## 背景

隨著創作輔助 AI 的普及，簡單的 Prompt 生成已經無法滿足專業作家的需求。作家更需要的是「風格對齊」與「語感參考」。當前市面上的 RAG 系統多半針對「知識問答」設計，對於「小說文筆與節奏」的檢索效果極差。因此，我們必須放棄傳統的單一向量檢索，改採針對文學特性量身打造的三層式漏斗架構，兼顧檢索深度與運算成本。

## 詳細內容

### 🟢 Layer 1：元數據過濾（硬條件篩選）
基於 SQLite 打造的極速篩選層，負責第一步的「大範圍瘦身」。
透過關係型資料庫的優勢，能以微秒級的延遲處理分類檢索，確保我們不會把古代武俠的段落錯配給現代都市的場景。
*   **過濾維度**：書名、作者、標籤（Tags）、總字數、讀者評分、類型（13 類大項）。
*   **效能指標**：檢索延遲 < 10ms，快速縮小候選範圍至 10%。

### 🔵 Layer 2：寫作指紋庫（風格特徵初篩）
這是本系統最獨特的創新。透過純 CPU 計算的 5 組統計特徵，將文本的「語感」量化。由於不依賴神經網絡，每秒可比對上百萬筆資料。

| 特徵維度 | 描述說明 | 計算邏輯與閾值 |
| :--- | :--- | :--- |
| **句長分布** | 反映寫作節奏（短平快 vs 雋永長句） | 計算逗號至句號間的平均字數與方差 |
| **標點節奏** | 判斷文本張力與呼吸感 | 逗號、句號、驚嘆號的相對密度比例 |
| **情感詞頻** | 確認段落的基調（溫馨、壓抑、激烈） | 比對自建的 2,000 字正負向情感詞典 |
| **對話比例** | 區分「敘事推動」與「對話推動」 | 統計引號內文字佔整個段落的百分比 |
| **視角密度** | 人稱代詞的切換頻率與主觀性 | 第一人稱（我）與第三人稱（他/她）頻譜 |

### 🔴 Layer 3：向量語義檢索（深度語意比對）
在經過前兩層過濾後，將剩下高度潛力的段落送入 LanceDB 進行向量比對。
*   **向量庫庫體**：LanceDB（本地文件型資料庫，無 Server 架構，省去維運成本，完美整合 Python）。
*   **檢索算法**：ANN 近似最近鄰（Cosine 相似度）。
*   **Embedding 模型 A/B 測試**：
    *   *方案 A：BGE-M3*（多語言，繁中支援極佳，適用於大範圍跨語系語境，可採用 GGUF 格式降級跑 CPU）。
    *   *方案 B：Qwen3-Embedding-4B*（阿里開源，中文網文語料訓練多，創作類文本語意捕捉更精準）。
    *   *測試指標*：檢索相關性 @Top-5（人工盲測）、計算速度、VRAM 佔用空間。

### 漸進向量化策略
面對龐大的語料庫，我們採用分階段推行策略，避免初期算力卡脖子：
*   **Phase 1**：首批 500 本精選（依據平台評分與下載總量篩選），快速跑通三層 Pipeline。
*   **Phase 2**：擴建至 2,000 本，主要以豐富「懸疑」、「百合」等長尾標籤為主。
*   **Phase 3**：全量網文語料庫向量化（需視伺服器 VRAM 與最終端儲存空間動態調整）。

## 實戰範例

以下為系統核心中，串接三層檢索漏斗的代碼實作範例：

```python
import sqlite3
import numpy as np
import lancedb
from models import load_model
from utils.feature_extractor import extract_fingerprint

# 全局模型初始化
model = load_model("Qwen3-Embedding-4B")
db = lancedb.connect("./data/novel_vector_store")
lancedb_table = db.open_table("novel_chunks")

def search_similar_style(query_text: str, top_k: int = 5):
    """
    給定一段目標文字，找最相近的參考段落
    """
    # 🟢 Layer 1: 元數據過濾 (SQLite)
    # 取得符合特定類型與高評分要求的書籍 ID
    candidates_ids = sqlite_filter(genre=["言情", "現代"], min_rating=4.5)
    
    # 🔵 Layer 2: 寫作指紋初篩 (CPU 特徵比對)
    # 提取當前輸入文本的 5 維節奏指紋
    fingerprint = extract_fingerprint(query_text)
    # 過濾出風格相似度高於 0.7 的段落
    candidates = fingerprint_filter(candidates_ids, fingerprint, threshold=0.7)
    
    # 🔴 Layer 3: 向量語義檢索 (LanceDB)
    # 將文本轉化為稠密向量，並在 Layer 2 篩選出的範圍內進行 ANN 檢索
    embedding = model.encode(query_text)
    
    # 加入 prefilter 將 LanceDB 的檢索限縮在 candidates 名單中
    results = (lancedb_table.search(embedding)
               .where(f"chunk_id IN {tuple(candidates)}")
               .limit(top_k)
               .to_list())
               
    return results
```

## 注意事項

⚠️ **資源管理警告**
1. **GPU 記憶體（VRAM）**：Embedding 模型推理時需高度仰賴 GPU 加速。BGE-M3 約佔用 1.5GB VRAM；切勿與主寫作大模型（如 LLM 本體）同時並發全速運作，極易導致 VRAM OOM（Out Of Memory）。
2. **建庫效能**：首次建立 500 本書的向量庫非常耗時。請務必使用 `batch_size=32` 或以上的批次矩陣運算，切勿逐句 input。

⚠️ **LanceDB 維護機制**
LanceDB 雖然極度輕量，但底層為不可變數據結構。每次批量新增文件段落（Chunks）之後，務必在深夜閒置時段執行 `rebuild_index()`，否則 ANN 檢索的精準度與效能會隨數據增量而快速衰減。
