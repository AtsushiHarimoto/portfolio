# 07.9 SDXL / Flux LoRA 訓練工作流設計 — 從零打造角色一致性模型

> **類型**: 工程實戰 + 機器學習
> **日期**: 2026-03-26
> **來源**: LoRA 訓練多輪迭代實戰

---

## 摘要

在生成式 AI 與 AIGC 落地應用的範疇中，「角色一致性 (Character Consistency)」始終是核心痛點。LoRA (Low-Rank Adaptation) 技術的引入，為這個問題提供了解決方案。透過凍結龐大的基礎模型 (Base Model) 權重，並平行注入低秩矩陣進行微調，我們能夠以極低的 VRAM 成本與計算資源，將高維度的潛在空間特徵（Latent Space Features）強力錨定到特定的角色屬性上，保證角色在不同視角、不同打光與不同環境下的 IP 約束力。

本文旨在建立一套標準化的工程實戰工作流，從資料集萃取、超參數調優到自動化評估矩陣，系統化解構 SDXL 與 Flux.1 架構下的 LoRA 訓練機制。我們將摒棄「煉丹式」的盲目試錯，確立以指標驅動 (Metrics-driven) 的微調管線，確保最終產出的模型具有高泛化性與極高的人臉/特徵相似度。

> [!NOTE]
> 💡 **白話文解釋**：想像基礎模型是一個繪畫技巧高超但「重度臉盲」的素描大師。他能畫出完美的賽博龐克城市或精美的洋裝，但每次畫同一個人的長相都不太一樣。LoRA 訓練就像是為這位大師配製一副「專屬特製眼鏡」，只要戴上這副眼鏡（掛載 LoRA 模型），大師大腦中的繪畫技巧不變，但他會瞬間「記住這個特定學生的臉孔特徵」，從而精準畫出同一個人的各種姿態。

## 背景

隨著開源文生圖模型的演進，我們已經擁有 SD 1.5、SDXL 到當前極具統治力的 Flux.1 等強大基底。然而，這些基礎模型是利用數十億張廣泛圖像訓練而成的，它們學會了「人類」這個泛化概念的強大先驗知識，卻無法精確記住「專屬於你的虛擬偶像或 IP 角色」。

在商業應用場景（如漫畫連載、遊戲素材生成、虛擬網紅營運）中，若我們單純以提示詞（Prompt）如 `a young girl, blue eyes, silver twin-tails, mechanical rabbit ears` 進行描述，模型每次在 Diffusion 降噪過程中「擲骰子」所生成的細節組合必定存在隨機性。這使得同一個角色在上一張圖是鵝蛋臉，下一張圖卻變成瓜子臉，衣物的機械結構也會發生位移。因此，從零設計並執行一套嚴謹的角色 LoRA 訓練工作流，是每一個 AI 工程師與美術技術（TA）必須掌握的關鍵能力。

## 詳細內容

### 1. LoRA 訓練前的資料準備

無效的 Garbage In 必然導致 Garbage Out，資料集的品質是決定角色一致性上限的唯一要素。我們建議的資料準備規範如下：

*   **訓練圖像數量：** 針對單一角色，**最佳甜區（Sweet Spot）落在 20 至 50 張**。少於 20 張極易引發過擬合（Overfitting），導致模型只會生成特定的姿勢；大於 50 張則會陷入邊際效益遞減，且增加人工清理與打標（Captioning）的負擔。
*   **構圖多樣性：** 必須強制包含不同焦段的影像，建議比例為：**面部特寫 (Face Close-up) 40%、半身像 (Upper Body) 40%、全身像 (Full Body) 20%**。此外，需涵蓋俯視、仰視、側臉（Profile）等多元視角。
*   **影像打標 (Captioning) 策略：**
    *   二次元/動漫風格：建議使用 **WD 14 Tagger (ConvNext v2)** 或更新的版本提取 Booru 標籤。
    *   寫實/3D風格：建議使用 **BLIP-2** 或 **Florence-2** 生成自然語言描述（Natural Language Captions）。
    *   **Trigger Word 綁定：** 必須在所有標註的開頭加入自定義的觸發詞（例如 `chunxiao_char`）。工程上的關鍵技巧是**「標註剝離 (Tag Pruning)」**：若你希望角色永遠具有「綠色瞳孔」，你必須從標籤檔案 (`.txt`) 中把 `green eyes` 刪除。這樣一來，模型就會把綠色瞳孔的特徵，強制綁定並壓縮到 `chunxiao_char` 這個觸發詞中。
*   **資料夾結構：** 遵循 `kohya_ss` 或 `sd-scripts` 的標準格式：
    ```bash
    workspace/
    ├── img/
    │   └── 40_chunxiao/  # 40代表每張圖的 repeats (重複訓練次數)
    ├── log/
    └── model/
    ```

### 2. SDXL vs Flux 訓練差異

SDXL 與 Flux 架構在參數量（3.5B vs 12B）與文本編碼器（雙 CLIP vs CLIP + T5）上有顯著差異，這直接影響了我們的工作流設計：

| 評估維度 | SDXL LoRA | Flux.1 LoRA |
| :--- | :--- | :--- |
| **訓練框架** | sd-scripts / kohya_ss | sd-scripts / SimpleTuner |
| **建議 Base Model** | SDXL 1.0 base | Flux.1 [dev] |
| **推薦 Rank (dim)** | 16 ~ 32 | 8 ~ 16 (因參數量大，低 rank 即足夠) |
| **VRAM 需求** | 12GB ~ 16GB (開啟 bf16) | > 24GB (推薦 40GB+，如 RTX A6000) |
| **Text Encoder 訓練**| 通常同時訓練 (TE1 & TE2) | 暫不建議/無法訓練 T5 (VRAM 消耗巨大) |
| **Optimizer 推薦** | AdamW8bit / DAdaptation | Adafactor / Prodigy |
| **訓練時長 (4090)** | 1 ~ 2 小時 | 4 ~ 6 小時 |
| **預期品質與特點**| 寫實度佳，但面對複雜肢體可能崩壞 | 擁有驚人的文本服從度與解剖學準確性 |

### 3. 關鍵訓練超參數

超參數矩陣的設定是微調工藝的核心。以下針對角色一致性目標，拆解幾項最關鍵的數值：

*   **Rank (`network_dim`) 與 Alpha (`network_alpha`)：**
    *   **Rank (秩)** 決定了低秩矩陣的資訊容量。對於單一角色，我們只需要儲存其臉部與衣服的局部特徵，SDXL 建議 `dim=32`，Flux 建議 `dim=16` 即可。若 rank 開到 128，只會徒增檔案大小與訓練雜訊。
    *   **Alpha** 作為縮放因子，用以平衡梯度更新幅度。工程實踐中的防呆設定是 `Alpha = Rank` 或是 `Alpha = Rank // 2`。
*   **Learning Rate (學習率)：**
    *   SDXL 下：U-Net LR 設為 `1e-4`，Text Encoder LR 更敏感需設為 `1e-5`。
    *   Flux 下：若使用 Adafactor，推薦 LR 設為 `4e-4` 至 `1e-3` 區間。
*   **Gradient Checkpointing (梯度檢查點)：**
    *   **必須開啟。** 雖然會增加約 20%~30% 的運算時間（時間換空間），但能大幅降低反向傳播時的記憶體激增，是民用級 GPU (如 RTX 4090) 能夠訓練的救命稻草。
*   **Batch Size (批次大小)：**
    *   強烈取決於 VRAM。以 24GB VRAM 為例，開啟 Gradient Checkpointing 後，SDXL 可將 Batch Size 設為 `2` 到 `4`；而 Flux 通常只能乖乖設定成 `1`。

### 4. sd-scripts 訓練指令範例

以下提供基於 Linux/WSL 環境，針對 SDXL 角色的自動化 Bash 腳本範例，調用 HuggingFace `accelerate` 進行多執行緒加速：

```bash
#!/bin/bash
# train_lora_chunxiao.sh

MODEL_NAME="stabilityai/stable-diffusion-xl-base-1.0"
TRAIN_DIR="./img"
OUTPUT_DIR="./model"
LOG_DIR="./log"

accelerate launch --num_cpu_threads_per_process=8 train_network.py \
  --pretrained_model_name_or_path=$MODEL_NAME \
  --train_data_dir=$TRAIN_DIR \
  --output_dir=$OUTPUT_DIR \
  --output_name="chunxiao_xl_v1" \
  --logging_dir=$LOG_DIR \
  --resolution="1024,1024" \
  --network_module="networks.lora" \
  --network_dim=32 \
  --network_alpha=16 \
  --optimizer_type="Adafactor" \
  --optimizer_args "scale_parameter=False" "relative_step=False" "warmup_init=False" \
  --lr_scheduler="cosine_with_restarts" \
  --lr_scheduler_num_cycles=1 \
  --learning_rate=1e-4 \
  --unet_lr=1e-4 \
  --text_encoder_lr=1e-5 \
  --max_train_epochs=10 \
  --save_every_n_epochs=2 \
  --mixed_precision="bf16" \
  --save_precision="bf16" \
  --gradient_checkpointing \
  --cache_latents \
  --cache_latents_to_disk \
  --xformers \
  --bucket_no_upscale \
  --bucket_reso_steps=64
```

### 5. 訓練過程監控

將數據紀錄寫入 `--logging_dir` 後，我們應在終端機啟動 TensorBoard (`tensorboard --logdir=./log`) 即時監控：

1.  **Loss 曲線解讀：** 擴散模型的 Loss 圖表通常呈現「鋸齒狀下降」，這是因為每次加噪/去噪任務難度不同。如果平滑處理 (Smoothing) 後的 Loss 趨勢線從 0.15 漸緩降至 0.08 左右趨於平滑，代表收斂良好。
2.  **何時 Overfit：** 若 Loss 降至 0.05 以下甚至逼近 0，往往是災難的開始。此時模型已經放棄「理解」圖像，而是開始「死背」訓練集，導致生圖結果出現高對比、顏色焦糊 (Deep-fried) 且無法應用不同 Prompt 進行變換。
3.  **Grad Norm (梯度範數)：** 監控梯度的波動，如果出現極端的尖刺（Spike），代表遇到了壞數據（全黑圖/損壞圖像）或學習率過高，引發了梯度爆炸。

### 6. 品質評估流程

「感覺像不像」是不夠客觀的，必須導入自動化的量化與質化評估管線。
我們通常會在 **ComfyUI** 內部建立自動評估 Workflow：

1.  **Prompt 矩陣出圖測試：** 置入 `XY Plot` 節點。X軸綁定 LoRA 權重 (如 0.6, 0.8, 1.0)，Y軸綁定測試提示詞。提示詞必須包含：極端視角（如 `#from above`）、動態動作（如 `#holding a sword, jumping`）以及風格轉換（如 `#cyberpunk style, watercolor`）。
2.  **Face Similarity 指標：** 將出圖結果送入含有 **ArcFace** 或 **InsightFace** 模型的評估節點中，與 Ground-Truth (真實角色的標準設定圖) 進行 Cosine Similarity (餘弦相似度) 計算。
3.  **主觀評分標準：** 
    *   1）角色特有配件（如：不對稱髮飾、淚痣）是否在不提 Prompt 的情況下自動生成。
    *   2）背景是否乾淨，沒有把訓練圖的房間背景也一併「黏」到角色身上。

## 常見失敗模式與解法

在從零到一打造工作流時，工程師最常面臨的阻礙及其修正方法總結如下表格：

| 異常現象 | 可能原因 (Root Cause) | 工程解法與修正策略 |
| :--- | :--- | :--- |
| **訓練崩潰 (Loss=NaN)** | 學習率設定過高，引發梯度爆炸；或 VAE 未開啟 fp32 精度。 | 將優化器換為 `AdamW8bit`，啟用 `--no_half_vae`，並調降基礎學習率 10 倍測試。 |
| **臉部模糊 / 細節丟失** | 解析度不足 (`512x512`) / 臉部特徵被「過度標註」導致模型不把它與核心詞綁定。 | 採用 `1024x1024` Bucket 訓練；使用正則化修剪標籤，拿掉如 `blue eyes` 等核心屬性標籤。 |
| **風格洩漏 (Style Bleed)** | 訓練集背景太雷同（例如都在同一張沙發上拍攝），模型將背景誤認為角色的本體。 | 在打標時強制加入 `simple background, white background` 進行特徵解耦；補充少數純色背景替補圖。 |
| **顯存溢出 (VRAM OOM)** | 顯存裝不下 Unet + TE 的反向傳播。 | 堅決啟用 `--gradient_checkpointing`，Batch Size 縮為 1，卸載 GUI，關閉不必要的背景服務。 |

## 迭代改進策略

真實開發環境中，極少有人一輪就能鍊出完美模型，必須依賴科學化的**迭代循環 (Iteration Loop)**：

1.  **Epoch 對比：** 在訓練指令中透過 `--save_every_n_epochs` 保存斷點。經過上述 ComfyUI 評估，若發現 Epoch 10 的模型僵化（無法做動作），而 Epoch 6 的相似度偏低但在動作泛化性極好；這暗示目前的資料表現域在中間 Epoch。
2.  **調整 Rank / LR：** 如果模型一直記不住細節裝備，在排除標籤問題後，應提高 Rank (如從 16 升至 32) 以擴充容量，並微幅提升 U-Net LR。
3.  **打磨資料集：** 如果跑了三輪依然有「風格洩漏」或「某個視角崩壞」，終極解方永遠是**切換回資料端**。砍掉品質差的低解析度圖，補足該特定視角的高解析度素描或截圖。

## 案例研究

**專案對象**：針對公司虛擬實況主 (VTuber) 角色「**春曉**」建立專屬 Flux LoRA。
**角色特徵**：擁有薄荷綠挑染短髮、右眼配戴機械單片眼鏡 (Mechanical monocle)、身穿戰術護甲。

*   **Iteration 1 (首輪盲測)：**
    取 30 張設定立繪，Rank 16，預設 LR。
    *   *評估結果*：Cosine Similarity = 0.35。薄荷綠挑染成功，但右眼的「機械單片眼鏡」時有時無，模型將其視為普通的金屬眼鏡，甚至長到左眼上。
*   **Iteration 2 (資料與標籤對齊)：**
    將資料集中大量包含臉部的圖片進行裁切（Crop），強調眼鏡部分，並在標記檔案中全面刪除 `monocle`, `eyewear`, `goggles` 等概念，迫使模型將「右眼機械眼鏡」的幾何特徵徹底綁定至觸發詞 `chunxiao_char`。
    *   *評估結果*：Cosine Similarity = 0.45。眼鏡問題大幅改善，但當生成的 Prompt 要求「穿著泳裝」時，模型出圖會出現殘留的「戰術護甲」碎片（過擬合至衣服）。
*   **Iteration 3 (解耦與超參微調)：**
    進一步在標記檔加上 `tactical armor, bulletproof vest` 以作為解耦提示，並將學習率調降至微調等級的 `1e-4` (配合 AdamW)，延長 Epoch 至 15 輪。
    *   *最終產出*：Cosine Similarity 穩定維持在 **0.55 ~ 0.60** 區間。「春曉」可完美執行各類高難度動作與變裝（泳裝、西裝），面部特徵釘死且零背景洩漏，達到工業級可交付水準。

## 總結

設計高效穩定的 LoRA 訓練工作流，本質上是一個將「非結構化資料特徵」映射至「高維神經網路」的軟體工程命題。從精確的資料集修剪、超參數矩陣的試算，再到自動化的相似度評估管線，每一個環節都需嚴密監控。捨棄「玄學抽卡」與單純碰運氣的心態，以工程指標為導向的迭代策略，才是現今在 SDXL 或 Flux 環境下維持角色 IP 絕對一致性的不二法門。
