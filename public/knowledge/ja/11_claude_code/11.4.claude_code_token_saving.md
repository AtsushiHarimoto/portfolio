# 11.4 C​laude Code トークン節約戦略：完全ガイド

> **種類**: ベストプラクティス + ツール設定
> **日付**: 2026-03-27
> **ソース**: C​laude Code 実践ツールチェーン設定の経験

---

## 概要

AI 主導の自動プログラミング環境において、トークンはAPIコストを意味するだけでなく、モデルの推論速度とコンテキスト記憶能力を直接的に決定します。本記事では、私たちの C​laude Code 開発環境で実装されている、完全なトークン節約ツールチェーンについて深く掘り下げます。ターミナル出力のインターセプトと圧縮（RTK、tokf）、ネイティブファイルの読み取り制限（`permissions.deny`）、ツール呼び出し方法の最適化（PTC）、およびAIモデルを動的に切り替えるルーティング戦略を通じて、不要なコンテキスト消費を60%以上大幅に削減し、複雑な推論タスクのために十分な記憶力と計算能力を確保することができます。

> [!NOTE]
> 💡 **分かりやすい解説**：トークンを海外旅行時の「手荷物重量制限」だと想像してみてください。家全体（完全な `npm install` のログや10万行の lock ファイルなど）をスーツケースに詰め込むと、重量オーバーの罰金（API予算超過）を取られるだけでなく、目的地に到着してから必要な服を見つけるのも困難になります（モデルの記憶喪失）。私たちの節約戦略は、自動化された「衣類用圧縮袋」のようなものです。

## 背景

開発者が C​laude Code などのエージェント型（Agentic）開発ツールへの依存を深めるにつれて、しばしば見落とされがちな隠れた障害が浮上し始めました。それは**「冗長なログによるコンテキストのオーバーフロー」**です。

Claude がバックグラウンドで日常的な開発コマンド（例えば `npm install`、`cargo build`、`git diff`、または各種テストコマンドなど）を実行する際、多くの場合、数百から数千行にも及ぶターミナル出力を伴います。これらの出力は、人間の開発者であればサッと読み飛ばせるかもしれませんが、AIの視点では、すべての文字が正確にコンテキストウィンドウ（Context Window）としてカウントされます。

この状況は3つの深刻な問題をもたらします：
1. **膨大なAPIコスト**：まったく価値のない依存パッケージのインストールログが、計算のためにモデルへ繰り返し送信されます。
2. **応答遅延の急増**：コンテキストが大きくなるにつれて、モデルとのやり取りにおける遅延（TTFT：Time to First Token）が著しく増加します。
3. **アテンションの希釈（Attention Dilution）**：数万ものトークンが複雑なシステムのデフォルト出力で埋め尽くされると、コアとなるビジネスロジックに対するモデルの注意力が大幅に低下し、前の手順の指示を「忘れる」という状況さえ発生します。

## コア戦略

### 1. RTK：Bash出力圧縮 (Rust Token Killer)

RTK は C​laude Code の `PreToolUse` フック（hook）メカニズムを利用し、Bashツールが出力をAIに返す前に、インテリジェントなインターセプトと圧縮を行います。

- **動作メカニズム**：`git`、`npm`、`cargo`、`docker` などの高頻度コマンドを対象に圧縮を行います。
- **スマートフォールトトレランス設定**：`[tee]` セクションに `mode = "failures"` を設定します。これにより、テスト失敗時には完全な出力を保持し、成功時には極限まで圧縮します。
- **節約効果**：コマンドの無駄な出力を60–90%削減します。

### 2. tokf：補完的フィルタリング機能

同じく `PreToolUse` フックを利用し、RTKの補完層として機能します。非標準フレームワークの残存する冗長なログをカバーします。Rust 1.93以上が必要です。

### 3. permissions.deny：ファイル読み取りのインターセプト

`.claude/settings.json` にdeny配列を設定し、巨大な自動生成ファイルを Claude が誤って読み込むのを防ぎます：

```json
{
  "permissions": {
    "deny": ["node_modules/**", "**/*.lock", "dist/**", ".next/**", "**/*.log"]
  }
}
```

各 lock ファイルのインターセプトにより、ファイルあたり 30k–80k トークンを節約できます。

### 4. PTC原則：一括ファイル読み取り

複数のファイルの特定の部分を抽出する場合、Readツールを複数回呼び出してファイル全体を読み込むのではなく、Bashの `grep` や `awk` を使用して一度に取得することを優先します。

### 5. AIモデルの割り当てとルーティング

3層アーキテクチャを採用：**Opus**（複雑な推論）→ **Sonnet**（主要なコーディング）→ **Antigravity/Gemini**（UI/ルーティン作業）。タスク前の出力の複雑さ評価タグにより、最適なモデルが確実に選択されるようにします。

## 3層設定アーキテクチャ

| 設定レベル | ファイルパス | コアの責務 |
|---------|---------|---------|
| **行動指示層** | `~/.claude/CLAUDE.md` | AIルーティングルール、タスク前クイックチェックのフォーマット、PTC原則 |
| **システム設定層** | `.claude/settings.json` | `permissions.deny` + Hook設定 |
| **オンデマンド読み込み層** | `.claude/rules/token-tools-setup.md` | インストールガイド（通常時はコンテキストに読み込まない） |

## 実践的な効果

| ツールと戦略 | インターセプト対象 | 一般的な節約量 |
|----------|---------|---------|
| RTK | Bashツールの出力 | 60–90% |
| tokf | Bash出力の補完層 | 60–90% |
| permissions.deny | 大規模な自動生成ファイルの読み取り | 30k–80k tokens/file |
| PTC原則 | 複数回のRead → 1回のgrep | 60% |
| モデルルーティング | ルーティンタスクをGeminiに委任 | APIコストの大幅な削減 |

## クイックインストール

```bash
# RTK
cargo install --git https://github.com/rtk-ai/rtk
rtk init -g --auto-patch  # C​laude Code の再起動後に有効になります

# tokf (Rust 1.93以上が必要)
cargo install tokf
tokf hook install --global
```
